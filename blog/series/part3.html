In short

  • LoRA and QLoRA added about 14 points (28.49% to 42%), and a significance test says that is real, not luck.
  • Full fine-tuning added only 7.6 points, likely held back by 16-bit rounding: 92% of its weights never changed.
  • TinyLoRA added 2 points with SFT and GRPO alike, which could be luck; what its 13 numbers learned was the answer format.
  • Bonus: Claude Opus 5.5 edited 48,398 weights directly, with no training at all. It removed the "let me explain first" habit completely and landed at +1.6 points, right next to TinyLoRA.

Quick recap: I fine-tuned Qwen2.5-Coder-1.5B-Instruct (1.54 billion parameters) with the five methods from part 1, training TinyLoRA twice: once with supervised fine-tuning (SFT) and once with reinforcement learning (GRPO). Each model then answered the same 1,534 BIRD dev questions, and an answer counts as correct when its SQL returns the same rows as the reference ("gold") SQL. That score is execution accuracy (EX); part 2 has the setup. At the end there is a bonus sixth method: weight-space programming, where an LLM edits the weights directly.

Is it real or luck?

A score can go up by luck. So before believing any of this, I want to know: could a gain this size happen by chance?

Count what changed, not the totals

Most questions don't change at all: both models get them right, or both get them wrong. Those tell us nothing about which model is better. What matters are the questions where the two models disagree. There are two kinds:

  • Fixed: the base model was wrong, the tuned model is right.
  • Broke: the base model was right, the tuned model is wrong.

LoRA fixed 299 questions and broke 91. Check: 437 + 299 − 91 = 645, which is exactly LoRA's count of correct answers.

The coin-flip story

Imagine fine-tuning did nothing useful and just shuffled the model's mistakes around. Then every question where the two models disagree is like a coin flip: heads it lands in "fixed", tails in "broke". Over many flips you would expect roughly half and half.

So the question becomes: if I flip a fair coin 390 times (299 + 91), how likely is a split as lopsided as 299 to 91, or worse? That probability is the p-value. A small p means "a fair coin would almost never do this", so the change is probably real. A common rule of thumb: under 0.05 (1 in 20) counts as real. This test is called McNemar's test.

A tiny example you can do by hand. Say a method fixed 9 questions and broke 1: 10 coin flips. There is 1 way to get zero tails and 10 ways to get exactly one tail, so 11 of the 210 = 1,024 possible outcomes are this lopsided. It could also go the other way round (1 fixed, 9 broke), so double it: 2 × 11 / 1,024 = 0.021. About a 2% chance. Probably real.

Here is the same thing in Python. It is the exact calculation I used for every row below:

from math import comb

def mcnemar_p(fixed, broke):
    n = fixed + broke          # questions where the two models disagree
    k = min(fixed, broke)      # the smaller side
    # chance a fair coin gives a split at least this lopsided, either way round
    p = 2 * sum(comb(n, i) for i in range(k + 1)) / 2**n
    return min(p, 1.0)

print(mcnemar_p(9, 1))       # 0.021484375
print(mcnemar_p(299, 91))    # 5.6e-27   (LoRA)
print(mcnemar_p(160, 130))   # 0.088     (TinyLoRA + GRPO)

comb(n, i) counts the ways to get i tails in n flips.

What the base model got wrong, and what fine-tuning fixed

The most useful thing I did was look at how the base model fails. 693 of its 1,534 queries don't even run. And 602 of those 693 fail with the same SQLite error: no such column. The model writes valid SQL. It just names columns that aren't there, often a column that does exist, but in a different table.

Example 1: the column is in the other table

From the toxicology database (question 261):

Write down bond id for molecules that are carcinogenic. (Hint from BIRD: label = '+' means molecules are carcinogenic.)

Base model:

SELECT bond_id FROM bond WHERE label = '+'

SQLite answers no such column: label. The label column lives in the molecule table, not in bond. The funny part: in its explanation, written just before this SQL, the base model says so itself: "The information about molecules and their labels is stored in the molecule table." Then it writes the query against bond anyway.

After LoRA:

SELECT T1.bond_id
FROM bond AS T1
INNER JOIN molecule AS T2 ON T1.molecule_id = T2.molecule_id
WHERE T2.label = '+'

It joins bond to molecule through the shared molecule_id column and filters on the right table. Every fine-tuned model got this one, including both TinyLoRA runs (they used a subquery instead of a join).

Example 2: full fine-tuning repeats the mistake, LoRA doesn't

From the superhero database (question 755):

List down at least five full name of Demi-God superheroes. (Hint: Demi-God superheroes refers to race = 'Demi-God'.)

The base model and the fully fine-tuned model wrote the exact same query:

SELECT full_name FROM superhero WHERE race = 'Demi-God' LIMIT 5

Again no such column: race. The superhero table only has a race_id; the names of races live in a separate race table. LoRA:

SELECT T1.full_name
FROM superhero AS T1
INNER JOIN race AS T2 ON T1.race_id = T2.id
WHERE T2.race = 'Demi-God' LIMIT 5

This pattern is common: it is part of the 170 vs 79 split between LoRA and full fine-tuning above.

Example 3: every model fails

633 questions were missed by all eight runs. This one is simple and instructive (codebase_community database, question 663):

What is the id of the youngest user? (Hint: the youngest user refers to MIN(Age).)

All seven fine-tuned models wrote this (LoRA-FA just left out the ASC):

SELECT Id FROM users ORDER BY Age ASC LIMIT 1

Looks right. But 32,007 of the 40,325 users have no age at all (NULL), and SQLite sorts NULL before every number. So this query returns a user with no age (Id −1), not the youngest user. The gold query uses WHERE Age = (SELECT MIN(Age) FROM users), which skips the NULLs and returns Id 805. (The base model wrote SELECT MIN(Age) FROM users, which returns an age, not an id.) None of the runs learned to watch out for empty values.

Full fine-tuning vs LoRA: why the biggest method lost

Full fine-tuning lets all 1.54 billion weights change, so you'd expect it to beat LoRA, or at least tie. It lost by six points, and the test above says that gap is real.

I don't think this means "full fine-tuning is worse". My best guess is that I crippled it to fit on the GPU. To keep memory down I stored its weights in bfloat16 (a 16-bit number format) with no 32-bit "master copy". A 32-bit master copy alone would have been another 1.54 billion × 4 bytes = 6.2 GB.

Why 16-bit weights can swallow small updates

bfloat16 keeps only about 2 to 3 significant digits. Near 0.05, the closest numbers it can store are 0.050049 and then 0.050293. The gap between them is 0.000244. Anything smaller than half that gap gets rounded away.

Full fine-tuning used a learning rate of 0.00001, and with the Adam optimizer each step moves a weight by roughly the learning rate, often less. So a weight of 0.05 gets a nudge of about 0.00001, which is far smaller than half of 0.000244. The nudge is rounded off and the weight doesn't change. You can see it in two lines:

import torch

w = torch.tensor(0.05, dtype=torch.bfloat16)
print(w.item())             # 0.050048828125  (closest bfloat16 to 0.05)
print((w + 1e-5).item())    # 0.050048828125  (the update vanished)

With a 32-bit master copy, the tiny nudges pile up there until they are big enough to show. Without one, they are lost every step.

I checked: most weights never moved

To see if this really happened, I compared the fully fine-tuned weights with the original weights, number by number. After 125 steps, 1,419,482,061 of the 1,543,714,304 weights (92%) are exactly the same, bit for bit. The weights that did move are almost all very small ones, where bfloat16's gaps are tiny. Among weights of size 0.0039 (2-8) or more, which is 84% of all weights, 99.99% never changed.

So "full" fine-tuning mostly tuned the smallest weights. LoRA didn't have this problem: its patch is stored in 32-bit, and it used a learning rate 20 times bigger (0.0002).

I measured that the rounding happened. I did not measure that the rounding is why it scored lower: I never reran it with a 32-bit master copy or more steps. So this stays my best guess, not a proven cause.

QLoRA: same score, least memory

QLoRA freezes the base model in 4-bit and trains the same LoRA patch on top. It scored 42.44% against LoRA's 42.05%. That is 651 vs 645 correct, six questions: the tie from the head-to-head test above.

The win is memory: 4.0 GB peak during training versus 5.0 GB for LoRA. The cost is time: 41.4 minutes versus 31.3, because the 4-bit weights have to be unpacked on every forward pass. On a 1.5B model 1 GB hardly matters. On a 7B or 13B model on a 16 GB card, it can decide whether you can train at all.

One detail for deployment: my 42.44% is the QLoRA patch merged into the original 16-bit weights. If you keep the base model in 4-bit when serving too, the score is 41.46%: 636 correct, 15 fewer. About one point, and with a head-to-head p of 0.26 even that could be noise. In my setup the 4-bit model was also slower to answer: 190 seconds for the whole dev set versus 110.

The TinyLoRA twist

This was the claim I most wanted to test. The paper behind TinyLoRA reports Qwen2.5-7B-Instruct reaching 91% on GSM8K (grade-school math word problems) by training just 13 numbers with reinforcement learning, and says supervised fine-tuning needs updates 100 to 1,000 times larger to get the same gains. The infographic I started from (see part 1) put it more bluntly: TinyLoRA only works with RL.

Same score, different models

Both TinyLoRA runs scored exactly 30.44%, 467 correct answers each. My first thought was a bug: did I evaluate the same model twice?

No. The two models disagree on 252 questions: 126 that only SFT got right and 126 that only GRPO got right. They just land on the same total. The 13 numbers they learned differ too: the two sets point in almost unrelated directions.

So on this task I could not confirm "TinyLoRA only works with RL". Plain SFT got the same +1.95 points in under a quarter of the time (30 minutes vs 128), and neither gain is clearly more than luck.

What the 13 numbers learned: format

The score barely moved, but the answers look completely different. My prompt asks the model to "Return only the SQL in a ```sql code block". The base model often ignores that. It likes to explain its plan step by step first, then give the SQL. Only 838 of its 1,534 answers start straight with the SQL block. After TinyLoRA, 1,525 (SFT) and 1,433 (GRPO) do.

The average answer shrank from 650 characters to 179 (SFT) and 239 (GRPO), close to LoRA's 173. Shorter answers mean less to generate: answering the whole dev set took the base model 506 seconds, and the TinyLoRA models 118 (SFT) and 133 (GRPO). About 4 times faster.

That is a real behaviour change from 13 numbers. But it is the wrong change for BIRD: writing SQL first doesn't tell the model that label lives in the molecule table. In the error table above, TinyLoRA barely dented "no such column", while LoRA halved it.

Did GRPO learn anything during training?

A little. The reward is the share of each step's 64 sampled answers that were correct (part 2 walks through the loop).

Averaged over 10 steps, the reward went from 26.7% in the first ten steps to 29.1% in the last ten. Single steps jump around because each draws new questions, so I trust the average more. A small climb, in line with the dev result: a little better, but not clearly more than noise.

Why my result differs from the paper

I don't think my result says the paper is wrong. I tested something different. My best guesses, most likely first:

  1. The task needs knowledge, not a nudge. On GSM8K, the 7B model probably already knows how to do most of the math. A small push in the right direction ("think step by step, then answer in this format") can unlock it. BIRD needs facts about the databases: which columns exist, in which tables, what the values look like. Thirteen numbers can change a style. I doubt they can store a map of table layouts.
  2. A short RL run. My GRPO run was 75 steps over 600 questions. The paper trains for far longer. RL might pull ahead of SFT with a bigger budget.
  3. A smaller model. 1.5B parameters vs 7B. A bigger model may have more hidden ability for 13 numbers to unlock.

Bonus method 6: weight-space programming

While I was writing this up, MIT CSAIL published Sparks of Weight-Space Programming. Instead of gradient descent, a frontier LLM read a small model's raw weights and edited them by hand. On Qwen3.5-0.8B it found a "looping" direction in two MLP layers, subtracted it from 0.016% of the weights, and MATH-500 went from 7.9% to 48.1%. Their own caveat: the edit fixed a habit that stopped the model from finishing, it did not make the model better at math. I repeated the experiment on my model, with Claude Opus 5.5 as the editor, running as an agent.

The rules

  • Read the weights, on CPU. A small Python library to load any weight matrix and compute whatever it likes: statistics, SVD, projections.
  • 25 forward passes, the only way to run the model. A pass either answers up to 512 practice questions with the original and the edited model side by side (graded), or records the model's inner activations on up to 1,024 texts.
  • Practice on BIRD's training questions only. The dev set, the other methods' weights and all results were off limits. I checked its logs afterwards.
  • No training. No gradients, no optimizer, no fitting weights to a loss. Edits go through a save_edit() function that refuses the embedding, the output layer, the final norm, and "multiply the whole matrix by a number".
  • Explain every step in a lab notebook.

What it found

It used 19 of its 25 passes, about an hour and a half in total. It started by reading failures and found the two habits from this post. For the wrong-table columns it traced the decision to a tug of war between attention heads and MLPs in layers 21 to 27, but every fix it tried broke about as many answers as it fixed on a fresh sample, so it threw them away.

The second habit was opening with "Let's walk through this..." instead of the SQL. The middle layers strongly prefer to start with ```, but a handful of neurons in the last MLP layers fire almost only at the first answer token and tip the model into prose. It also noticed this happens far more on long prompts.

The edit it submitted touches one matrix, the MLP output of the last layer (layer 27), and changes 32 of its 8,960 columns with a single rank-one patch:

W = load("model.layers.27.mlp.down_proj.weight")
# k: "where" - fires at the first answer token, near 0 everywhere else
# u: "what"  - the smallest change that lowers "Let" and "Here" by 5 nats
#             while leaving the 400 most common tokens exactly as they were
W[:, S] += torch.outer(u, k[S])      # S = the 32 columns that matter most
save_edit("model.layers.27.mlp.down_proj.weight", W)

Both vectors come from one step of linear algebra, not from training. 5 nats makes those two words about 150 times less likely at that one position. In total 48,398 weights changed, 0.003% of the model. On its practice questions the edit removed the habit but gained only about 1 question in 2,048, and it said so; it predicted any gain would show up on longer prompts.

Running it longer

MIT's best result needed 50 passes, and my editor stopped at 19. So a second run picked up from its edit with a much bigger budget: 84 passes in total, longer practice prompts (up to 3,072 tokens, like the dev set), and 44 candidate edits, most of them aimed at the wrong-table columns. Each was tested against F4, the first run's edit, on 256 practice questions.

Three candidates looked like wins: 96, 95 and 93 correct against F4's 91. Then each was re-tested on 256 fresh questions, and all three lost or tied: 81, 83 and 88 against F4's 88. None was kept.

That is the winner's curse. Picture 44 fair coins, each flipped 256 times. By pure chance a few will land heads noticeably more than half the time, and if you only look at the best coins, they look special. Test 44 edits on small samples and some will "win" by luck. The fix is the one used here: never trust a winner until it wins again on questions it has never seen.

So I ran a third round under rules written down before any test: at most 4 candidate edits, each with a predicted effect, tested against F4 on 1,024 fresh practice questions no earlier run had seen, and kept only if the gain was clearly not luck (p < 0.05). The editor tested one candidate. It had noticed that table names with spaces or hyphens, like Store Locations or voice-actors, must be wrapped in quotes in SQL, but the model copies them bare from the schema comments and the query crashes. It found a signal in the last layer that fires exactly where such a quote is needed, and added a second small patch (64 more columns, 96,429 weights) that pushes the quote character up by 4.5 nats, about 90 times more likely, at those spots only. On the fresh questions: 25 fixed, 7 broken, p = 0.002, inside the range it had predicted. The first confirmed gain from editing by hand.

Then the dev set: 30.05%, no change (15 fixed, 16 broken). The edit did not fail; the test set just rarely needs it. Of BIRD dev's 11 databases only one has a table name that needs quoting (order, a SQL keyword, in financial), and the bare name appears in 3 answers. That is the clearest lesson of method 6: a weight-space edit fixes exactly the habit you find, so it only pays off if your real data has that habit.

How it compares

It landed in the same place as TinyLoRA (30.12% vs 30.44%), for the same reason: it fixed the shape of the answer, not the model's knowledge of the databases. The two are still different models; they disagree on 217 questions. It is also the story MIT tells. Their looping stopped 93% of answers from ever finishing, so removing it unlocked a lot. My model's rambling usually still ended with a SQL block, so removing it unlocked little. Editing weights by hand can remove an obstacle you can see. It could not teach the model which column lives in which table.

Verdict: weight-space programming was greeted as a breakthrough, but on my task it was overhyped: 30.12% against the base model's 28.49% (p = 0.065, could be luck), gained by removing a habit rather than teaching anything new.

What I'd pick, and when

  • Default: LoRA. Tied for the best score, half an hour, 5 GB, and a small patch you can add to or remove from the base model.
  • Short on GPU memory: QLoRA. The same score with the least memory, but about a third slower to train. Serving in 4-bit costs around a point.
  • Full fine-tuning: only if you can do it properly. That means enough memory for 32-bit master weights, and probably more steps. Done the cheap way, as I had to, it lost to LoRA.
  • LoRA-FA: within 1.5 points of LoRA with 44% fewer trainable numbers. A fine option, but here QLoRA saved more memory and scored higher.
  • TinyLoRA: for tiny behaviour changes, like answer format or length, not for teaching the model about the databases. To try it with RL, pick a task with an automatic grader that needs a skill the model mostly has already, and plan for a long run.
  • Weight-space programming: a promising tool for removing one specific habit you can see and measure, with no training run. It did not add knowledge here, and it needs a strong editor model and careful checking.

Fine-tune your own model: a checklist

Everything this series taught me, in the order I would do it next time:

  1. Measure the base model first, and read its failures. My biggest single lesson came from counting error types: 602 of 693 failed queries were "no such column". That told me what fine-tuning needed to fix.
  2. Build an automatic grader, then test the grader. Grade the gold answers against themselves; mine scored 1,532 of 1,534 and the two misses had an explanation. If the model's output is code, run it in a sandbox (part 2).
  3. Freeze a test set and never tune on it. Every choice (method, learning rate, which edit to keep) is made on training data. The test set is scored once at the end.
  4. Start with LoRA. Rank 16 to 64 on all linear layers, learning rate around 2e-4, loss only on the answer tokens. Switch to QLoRA if the model does not fit. Full fine-tuning only with memory to spare for 32-bit master weights.
  5. Keep everything else fixed when comparing. Same data, same order, same steps, same prompt. Otherwise you are comparing setups, not methods.
  6. Judge with paired counts, not averages. Count fixed vs broke questions and check whether the split could be a coin flip (McNemar's test, above).
  7. Confirm winners on fresh data. If you tried many variants, the best one is probably partly lucky (the winner's curse, above).
  8. Look at what changed, not just the score. TinyLoRA and the weight-space edit barely moved the score but changed every answer's format. That is a real effect, and you only see it by reading the outputs.

The infographic: what held, what didn't

Back to the infographic from part 1.

What held up:

  • LoRA-style methods get most of the benefit while training a few percent of the weights. Here LoRA trained 4.8% and LoRA-FA 2.7%, more than the infographic's 70B figures (1.2% and 0.6%), because the percentage depends on model size, rank and which matrices you adapt.
  • QLoRA gives LoRA-level results with less memory, and LoRA-FA cuts trainable numbers with only a small loss.
  • TinyLoRA can change a model's behaviour with 13 numbers. The format shift is real and large.

What didn't hold up, on my task:

  • The easy reading that more trainable numbers means better results. Full fine-tuning, squeezed into 16 GB, came last of the big methods.
  • TinyLoRA only works with RL. SFT got exactly the same score as RL, in a quarter of the time. Neither gain was clearly more than luck.
  • 13 numbers as a way to teach a task. Enough to change the format. Not enough to learn which column lives in which table.

Caveats

  • One run each. One training run, one seed per method. Another seed could move any method by a point or two; the McNemar tests don't cover that.
  • A small training budget. Each supervised method saw 2,000 questions, once. Published LoRA runs on the full BIRD training set reach higher scores, and the ranking of methods could change with more data.
  • A short GRPO run (75 steps), as noted above.
  • Full fine-tuning had a handicap: 16-bit weights with no 32-bit master copy, as shown above. With a proper setup it would likely do better.
  • BIRD's gold answers are not perfect. Some gold queries are wrong, and some hints don't match the data. For example, on question 275 the hint says a double bond is bond_type = ' = ' (with spaces), but the database stores '='. All eight runs trusted the hint and got zero rows back. A few "misses" are the model disagreeing with a bad label, and a few "hits" are luck.
  • My prompt is generous. It shows example values for every column, which makes the base model stronger. Some reports put this model near 17% on BIRD dev. My 28.49% baseline is not comparable to those, and fine-tuning gains might look different with a bare schema.
  • Weight editing: one editor model, three rounds. 88 passes in total, all on BIRD's training databases. Habits found there do not always show up in the dev set, as round 3 showed.
  • One task, one model. SQL on a 1.5B coding model, not math on the 7B or 70B models the paper and the infographic are about.
